## Context

`shortlinks-cli` сейчас — отдельный таргет (`type: tool`), который собирается и
устанавливается независимо от приложения. Пользователю, чтобы получить CLI, нужно
выполнить отдельную сборку и вручную положить бинарь куда-то в `PATH`. Это лишний шаг
и источник рассинхрона версий CLI и app.

Ограничения проекта (см. `CLAUDE.md` и `bootstrap-shortlinks/design.md`):
- Без entitlements / App Sandbox — приложение свободно пишет в домашнюю директорию.
- Подпись — самоподписанный сертификат, `CODE_SIGN_STYLE: Manual`.
- Проект генерируется из `project.yml` через `xcodegen generate`; `.xcodeproj` не
  коммитится.
- Доменная логика — в `ShortlinksCore`, переиспользуется app и CLI.

Решение по месту установки (согласовано с пользователем): симлинк в `~/.local/bin`
без прав администратора, с подсказкой про `PATH`, если каталога там нет.

## Goals / Non-Goals

**Goals:**
- CLI доступен сразу после установки приложения — без отдельной сборки/установки.
- Один источник истины: CLI-бинарь внутри `Shortlinks.app`, собирается вместе с app.
- Простое, идемпотентное и безопасное включение/выключение доступности из терминала.
- Понятный статус установки и подсказка про `PATH`.

**Non-Goals:**
- Не меняем набор и поведение команд CLI (это остаётся в `cli-interface`).
- Не требуем прав администратора и не пишем в `/usr/local/bin`.
- Не правим `PATH` пользователя автоматически (только подсказываем как это сделать).
- Не делаем установщик/pkg — распространяется как `.app`.

## Decisions

### Решение 1: Вкладывать CLI-бинарь в бандл приложения

CLI-таргет остаётся отдельным продуктом сборки, но app-таргет получает на него
зависимость и copy-фазу, которая кладёт собранный `shortlinks` внутрь `Shortlinks.app`
в `Contents/MacOS/shortlinks` (стандартная директория исполняемых файлов бандла).
Copy-фаза подписывает бинарь при копировании тем же self-signed сертификатом
(«Code Sign On Copy»).

В `project.yml` это зависимость app → cli с копированием в destination `executables`:
```yaml
ShortlinksApp:
  dependencies:
    - target: ShortlinksCore
    - target: shortlinks-cli
      embed: true
      codeSign: true
      copy:
        destination: executables   # → Contents/MacOS
```
После правки — `xcodegen generate`.

*Альтернативы:*
- `Contents/Helpers/shortlinks` (через destination `wrapper` + subpath) — конвенция для
  вспомогательных бинарей, но усложняет конфигурацию; `Contents/MacOS` проще и
  стандартен для исполняемых файлов.
- Линковать CLI как подкоманду самого app-бинаря (argv[0]-диспетчеризация) — экономит
  один бинарь, но смешивает SwiftUI-app и CLI-процесс, ломает простую модель «вызвал
  `shortlinks` в терминале». Отвергнуто.

### Решение 2: Доступность через симлинк в `~/.local/bin`

Действие «Установить CLI» создаёт симлинк `~/.local/bin/shortlinks` →
`<bundle>/Contents/MacOS/shortlinks`. Симлинк (а не копия) гарантирует, что CLI всегда
соответствует текущему бандлу — обновил app, CLI обновился автоматически.

Логика (в `ShortlinksCore`, чтобы быть тестируемой и переиспользуемой):
- `CLIInstaller.bundledBinaryURL` — путь к вложенному бинарю относительно
  `Bundle.main.bundleURL`.
- `install()` — создаёт `~/.local/bin` при отсутствии, атомарно пересоздаёт симлинк
  (идемпотентно); если по пути посторонний объект — возвращает ошибку «конфликт».
- `uninstall()` — удаляет симлинк, только если он указывает на бандл Shortlinks.
- `status()` — `.installed(path)` / `.notInstalled` / `.conflict(reason)`, вычисляется
  по резолву симлинка и сравнению с `bundledBinaryURL`.

*Альтернативы:*
- `/usr/local/bin` — уже в `PATH`, но требует прав администратора на Apple Silicon.
  Отвергнуто пользователем в пользу беспарольного `~/.local/bin`.
- Копировать бинарь вместо симлинка — рассинхрон версий после обновления app.

### Решение 3: Подсказка про `PATH`

После установки приложение проверяет, есть ли `~/.local/bin` в `PATH`. Поскольку
GUI-приложение запускается не из интерактивного шелла, `ProcessInfo.environment["PATH"]`
ненадёжен для шелла пользователя. Поэтому проверка делается через запуск
`login`-шелла пользователя (`$SHELL -lic 'echo $PATH'`) и поиск каталога в результате;
при неуверенности — показываем подсказку (безопаснее показать лишний раз).

Подсказка содержит готовую строку для добавления в шелл-профиль, например
`export PATH="$HOME/.local/bin:$PATH"`.

*Альтернатива:* доверять `ProcessInfo.environment["PATH"]` — для GUI-процесса это PATH
из launchd, а не из шелла, поэтому ненадёжно. Отвергнуто.

### Решение 4: UI в Настройках

Раздел «Командная строка» на экране Настроек: статус (установлен/не установлен/
конфликт), путь, кнопки «Установить CLI» / «Удалить CLI», и блок с подсказкой про
`PATH` при необходимости. Вёрстка — по существующей теме (`Theme.swift`, акцент
`#2A6FDB`).

## Risks / Trade-offs

- **Подпись вложенного бинаря** → если CLI не подписан тем же сертификатом, Gatekeeper
  может блокировать запуск. *Mitigation:* «Code Sign On Copy» тем же identity, что и app.
- **`~/.local/bin` не в `PATH`** → команда установлена, но `shortlinks` «не находится».
  *Mitigation:* явная подсказка с готовой строкой экспорта `PATH`.
- **Битый симлинк после перемещения/удаления `.app`** → симлинк указывает в никуда.
  *Mitigation:* `status()` обнаруживает несуществующую цель и показывает «не установлен/
  конфликт»; повторная установка чинит.
- **Определение `PATH` через `$SHELL -lic`** → запуск стороннего процесса, возможны
  нестандартные шеллы. *Mitigation:* при ошибке/таймауте показываем подсказку по
  умолчанию (fail-safe в сторону показа).
- **Рост размера бандла** на размер CLI-бинаря — незначителен, приемлемо.

## Migration Plan

1. Правка `project.yml` (зависимость app → cli + copy-фаза), `xcodegen generate`,
   проверка наличия `Contents/MacOS/shortlinks` в собранном бандле.
2. Добавление `CLIInstaller` в `ShortlinksCore` + юнит-тесты на `status/install/uninstall`.
3. Раздел Настроек в app.
4. Обновление документации: `CLAUDE.md` (CLI больше не отдельное приложение) и спека
   `cli-interface` (как поставляется).

Откат: вернуть `project.yml` к раздельной сборке; CLI снова собирается отдельным
таргетом (он остаётся валидным `tool`-таргетом и так).

### Решение 5: Предложение установки при первом запуске

При первом запуске, если CLI не установлен, приложение показывает онбординг-предложение
(«Установить» / «Не сейчас»). Факт прохождения онбординга хранится в `UserDefaults`
(флаг `cliOnboardingShown`); предложение показывается максимум один раз. «Установить»
вызывает тот же `CLIInstaller.install()`, что и кнопка в Настройках. Если CLI уже
установлен, предложение не показывается вовсе.

*Альтернатива:* только ручная установка в Настройках — проще, но пользователь может не
узнать о CLI. Отвергнуто в пользу явного предложения один раз.
