## Context

Список ссылок (`LinkListView`/`LinkRow`) сейчас рендерит строки с единственным жестом —
тап открывает карточку (`model.openDetail`). Удаление есть только из карточки и только
по одной (`AppModel.delete(id:)` → `LinkStore.delete(id:)`).

Статус ссылки вычисляется в `Link.status(now:)` из двух полей: `consumedAt` (→ `viewed`)
и `expiresAt` (→ `expired`); иначе `active`. Манульного «выключения» нет — единственный
способ убрать ссылку из оборота — удалить её. `route()`/`performOpen()` в `AppModel`
блокируют переход для всего, что не `.active`, поэтому новый «выключенный» статус
автоматически заблокирует переход, если он не равен `.active`.

Хранилище — единый `links.json`, правки через `LinkStore.mutate`. Конфликты iCloud
сливаются по `id` (`ConflictMerge`). Swift language mode 5, без strict concurrency.
Доменная логика живёт в `ShortlinksCore` и переиспользуется app и CLI.

## Goals / Non-Goals

**Goals:**
- Множественный выбор и массовое удаление в списке через переключаемый режим
  редактирования.
- Контекстное меню по строке списка: открыть, копировать, (де)активировать, удалить.
- Ручная (де)активация ссылки как новое наблюдаемое состояние, сохраняемое на диск и
  блокирующее переход.
- Обратная совместимость формата `links.json` (старые записи без нового поля читаются).

**Non-Goals:**
- Новые команды CLI для (де)активации (`shortlinks disable/enable`) — вне итерации;
  CLI `list` лишь корректно отображает новый статус.
- Массовая (де)активация в режиме редактирования — пока только массовое удаление;
  (де)активация доступна по одной из контекстного меню.
- Отдельный фильтр/раздел «Деактивированные» в боковой панели и счётчик для него.
- Drag-select, горячие клавиши, undo удаления.

## Decisions

### Решение 1: Деактивация — отдельное поле `disabledAt: Date?`, а не переиспользование срока
`Link` получает новое опциональное поле `disabledAt: Date?`. Деактивация = установить
`disabledAt = now`; активация = `disabledAt = nil`.

- **Почему так:** деактивация семантически независима от срока и потребления; хранить
  её отдельным полем — не теряем исходный `expiresAt`, активация тривиальна и обратима.
- **Альтернатива (отклонена):** «выключать» ссылку, выставляя `expiresAt` в прошлое.
  Лоссово (теряется исходный срок), активация неоднозначна, ломает смысл `expired`.
- **Совместимость:** поле опциональное → старый `links.json` декодируется без ошибок
  (`Codable` по умолчанию допускает отсутствие optional). В `init` Link новый параметр
  идёт со значением по умолчанию `nil`, чтобы не ломать существующие вызовы
  (`Link.make`, `consume` и тесты).

### Решение 2: Новый кейс `LinkStatus.disabled` и приоритет в `status(now:)`
`LinkStatus` получает кейс `disabled`. Порядок вычисления в `status(now:)`:
`consumedAt` → `viewed`; затем `disabledAt` → `disabled`; затем `expiresAt<=now` →
`expired`; иначе `active`.

- **Почему такой порядок:** `viewed` (одноразовая сгорела) — терминальное и важнейшее
  состояние, его не должна перекрывать ручная деактивация. `disabled` ставим выше
  `expired`, чтобы после активации просроченная ссылка честно показала `expired`, а до
  активации пользователь видел именно «деактивирована» (явное действие важнее пассивного
  истечения для UX).
- **Следствие для перехода:** `route()` уже пропускает только `.active`, поэтому
  отдельная правка маршрутизации не нужна — `disabled` блокируется автоматически.
- **Отображение:** `StatusPill` и `Format.subtitle` получают ветку для `disabled`
  («Деактивирована», нейтральный/серый цвет в духе макета).

### Решение 3: Операция (де)активации в `LinkStore`
Добавляется `LinkStore.setDisabled(id:_ disabled:Bool, now:Date = Date())` поверх
`mutate` (координированная атомарная запись), по аналогии с `consume`/`delete`.
`AppModel` получает `setDisabled(id:_:)`/удобные `deactivate(id:)`/`activate(id:)` и
после мутации делает `reload()`.

- **Почему в Store:** доменная мутация хранилища должна жить рядом с `add/delete/consume`,
  а не в UI; так она доступна и для будущего CLI без дублирования.

### Решение 4: Режим редактирования — состояние в `AppModel`
В `AppModel`: `var editing = false` и `var selection: Set<String> = []`. Методы:
`toggleEditing()` (сбрасывает `selection` при выходе), `toggleSelect(id:)`,
`deleteSelected()` (через новый `LinkStore.delete(ids:)` или цикл в одном `mutate`),
`var canDeleteSelected: Bool`. Переключатель «Изменить/Готово» — в тулбаре списка;
массовое удаление — кнопка в нижней панели, появляющейся в режиме редактирования.

- **Почему в `AppModel`:** список — stateless `View` над `@Observable` моделью; выбор и
  режим естественно живут в модели рядом с `filter/selectedId`.
- **Массовое удаление одним `mutate`:** `delete(ids: Set<String>)` снимает N отдельных
  координированных записей до одной — атомарно и без гонок.
- **Подтверждение:** SwiftUI `.confirmationDialog`/`.alert` с числом выбранных, в духе
  существующего подтверждения удаления из карточки.

### Решение 5: Контекстное меню через `.contextMenu` на `LinkRow`
На `LinkRow` вешается `.contextMenu { … }` с пунктами: «Открыть» (`model.openLink`),
«Скопировать адрес» (`model.copy(link.fullURL)`), «Деактивировать»/«Активировать»
(в зависимости от `link.status()`), «Удалить» (роль `.destructive`). Пункт
(де)активации скрывается/недоступен для `viewed`-ссылки (активировать сгоревшую нечего).

- **Почему `.contextMenu`:** нативный путь правого/Control-клика в SwiftUI, не конфликтует
  с `onTapGesture`. В режиме редактирования контекстное меню можно не показывать
  (действия идут через выбор), чтобы не смешивать два режима.

## Risks / Trade-offs

- **Рост модели `Link` ломает существующие инициализаторы/тесты** → новый параметр
  `disabledAt` со значением по умолчанию `nil`; вызовы `Link.make`/`consume` не меняются.
- **CLI собирается из того же `ShortlinksCore`; новый кейс `LinkStatus` может потребовать
  обработки в `switch` CLI** → пройтись по `switch` над `status`/`LinkStatus` в
  `shortlinks-cli` и добавить ветку `disabled` (отображение в `list`).
- **Слияние конфликтов iCloud по `id`** → `disabledAt` едет внутри записи ссылки;
  отдельная стратегия слияния не нужна, но стоит убедиться, что `ConflictMerge` берёт
  более свежую версию записи (поведение не меняется относительно прочих полей).
- **Двусмысленность статуса деактивированной, но просроченной ссылки** → зафиксировано
  решением 2 (приоритет `disabled` над `expired`); задокументировано в spec-сценарии.
- **Случайное массовое удаление** → обязательное подтверждение с числом выбранных и
  сброс выбора при выходе из режима.
