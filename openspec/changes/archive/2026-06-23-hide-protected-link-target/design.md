## Context

Защищённая паролем ссылка раскрывает свою цель до проверки пароля в двух местах
app-слоя:

- `Sources/ShortlinksApp/Views/RedirectOverlay.swift` — в фазе `ready` строка
  `Text(link.target)` (стр. 45) рендерится безусловно, а `SecureField` показывается
  только при `link.isProtected` (стр. 65). То есть цель видна *над* полем пароля.
- `Sources/ShortlinksApp/Views/LinkDetailView.swift` — `InfoRow(label: redirectsTo,
  value: link.target …)` (стр. 71) показывает цель открытым текстом всегда.
- `Sources/ShortlinksApp/Views/LinkListView.swift` — строка списка (`LinkRow`)
  показывает цель через `Text(link.target)`, а `TargetIcon` — трёхбуквенный код её типа.

Проверка пароля уже существует: `Password.verify(_:against:)` (соль+SHA-256),
вызывается из `AppModel.confirmRedirect()`. Поле `Link.target` хранится открытым
текстом в `links.json`; `passwordHash` — единственная защищённая часть. Строки и
иконки идут только через реестры `Strings` (поверх `Localizable.xcstrings`) и `Icons`.

Изменение целиком в app-слое и презентационное: модель, `Password`, `LinkStore`,
формат хранения и CLI не затрагиваются.

## Goals / Non-Goals

**Goals:**
- В оверлее перехода защищённой ссылки не показывать цель — только адрес `sl://` и
  запрос пароля.
- В списке ссылок для защищённой ссылки не показывать цель — маска вместо текста и
  нейтральная иконка (замок) вместо кода типа.
- В карточке деталей защищённой ссылки показывать маску и кнопку «Показать»,
  раскрывающую цель после ввода верного пароля (с возможностью снова скрыть).
- Не менять поведение для незащищённых ссылок.
- Соблюсти конвенции: строки через `Strings`, иконки через `Icons`, без магических
  литералов во вью.

**Non-Goals:**
- Шифрование цели на диске. `target` остаётся открытым текстом в `links.json`.
- Скрытие цели в CLI (`shortlinks resolve`/`open`) и в любых не-GUI путях.
- Защита от подбора пароля (лимиты попыток, троттлинг) — как и в текущем оверлее.
- Изменение модели `Link`, формата хранения, схемы миграции.

## Decisions

### Решение 1: Маскирование в UI, а не шифрование секрета
Скрываем цель только в интерфейсе; на диске `target` остаётся как есть.

*Почему:* запрос пользователя сформулирован в терминах UI («звёздочки», кнопка
«Показать»), а реальная угроза — подглядывание/демонстрация экрана, не криминалистика
диска. Маскирование закрывает её малой ценой и без изменения формата данных.

*Альтернатива (отклонена):* шифровать `target` ключом, выведенным из пароля.
Дало бы настоящую секретность, но: пароль не хранится (только хеш) → ключ негде взять
без ввода; ломается фоновое открытие и CLI-резолв; нужен новый формат хранения и
миграция. Это отдельный, гораздо больший change — выходит за рамки задачи.

### Решение 2: Состояние раскрытия — локальный `@State` в выделенном компоненте
Вводим небольшой компонент строки деталей с собственным состоянием
(`masked → prompting → revealed`). Размещаем его в существующем файле
`Sources/ShortlinksApp/Views/LinkDetailView.swift` (слой Views), рядом с его
единственным потребителем. `LinkDetailView.infoCard` подставляет его вместо обычного
`InfoRow` при `link.isProtected`.

*Почему:* раскрытие — эфемерное состояние одного экрана; держать его в `AppModel` —
лишняя связанность. Сброс при смене ссылки — через `.id(link.id)` на компоненте, что
удовлетворяет сценарий «сброс раскрытия при уходе с карточки».

*Почему Views, а не DesignSystem:* компонент знает о домене (`Password.verify`,
`Strings`), тогда как DesignSystem-молекулы намеренно presentational — тот же `InfoRow`
принимает текст параметрами. Класть проверку пароля в `InfoRow.swift` нарушило бы это
разделение; в слое Views (который уже импортирует `ShortlinksCore`) — на своём месте.

*Альтернатива (отклонена):* состояние в `AppModel` — усложняет модель ради
презентационной мелочи. *Альтернатива (отклонена):* отдельный файл
`ProtectedTargetRow.swift` — потребовал бы правки `project.yml` + `xcodegen generate`;
для маленького компонента с одним потребителем не оправдано.

### Решение 3: Проверка пароля — существующий `Password.verify`, без новой крипто
И в оверлее (через имеющийся `confirmRedirect()`), и в деталях (прямой вызов
`Password.verify(input, against: link.passwordHash!)` из компонента, т.к. вью уже
импортирует `ShortlinksCore`). При несовпадении — встроенное сообщение об ошибке
(переиспользуем строку `Strings.Toast.wrongPassword`), цель не раскрывается.

### Решение 4: Оверлей — ветвление фазы `ready` по `isProtected`
Для защищённой ссылки: убрать `confirmBody` и `Text(link.target)`; показать иконку
замка (переиспользуем `Icons.Status.privacy` = `lock.fill`), пояснение
(`Strings.Redirect.protectedBody`) и `SecureField`. Незащищённый путь (включая режим
подтверждения) остаётся без изменений. Предупреждение об одноразовости остаётся
видимым в обоих случаях — оно не раскрывает цель. Адрес `sl://` уже в шапке оверлея.

### Решение 5: Маска фиксированной длины, общая строка и нейтральная иконка
Маска — фиксированные `••••••••` (не `repeat(count: target.count)`), чтобы не утекала
длина цели; у маски отключено `textSelection`, чтобы её нельзя было скопировать как
значение. Маску держим в `Strings` (`Strings.Common.targetMask` — она общая для списка и
деталей) ради конвенции «нет литералов во вью», хотя строка нелингвистическая.

Чтобы не раскрывать даже тип цели, в списке и в шапке деталей иконка `TargetIcon`
получает флаг `masked`: вместо трёхбуквенного кода типа показывается замок
(`Icons.Status.privacy`). `TargetIcon` остаётся presentational — знает только «показать
замок», но не «почему».

Новые строки: `Redirect.protectedBody`, `Detail.reveal` («Показать»),
`Detail.hide` («Скрыть»), `Common.targetMask` («••••••••»). Переиспользуем
`Common.password`, `Common.cancel`, `Toast.wrongPassword`. Новые иконки:
`Icons.Reveal.show = "eye"`, `Icons.Reveal.hide = "eye.slash"`; в оверлее и для маски-
иконки переиспользуем `Icons.Status.privacy` (`lock.fill`). Плоские строки живут в коде
через `L()`/`defaultValue` (ru — язык-источник) и в каталог не добавляются — так же
устроены все прочие плоские строки; `Localizable.xcstrings` держит только
plural-вариации.

## Risks / Trade-offs

- **Цель остаётся открытым текстом в `links.json` и доступна через CLI `resolve`/`open`**
  → Маскирование честно описано как UI-уровень (proposal + Non-Goals). Настоящая
  секретность — отдельный change с шифрованием; здесь не заявляется.
- **Владелец вводит пароль для своей же ссылки в деталях (лишний шаг)** → Сделано
  сознательно: защита от подглядывания/демонстрации экрана. Раскрытие — один клик +
  пароль, с обратным «Скрыть».
- **GUI не покрыт автотестами на CI** → Логика `Password.verify` уже покрыта
  `ShortlinksCoreTests`; новые правки чисто презентационные. Верификация — ручной
  чек-лист (сборка app + прогон сценариев из спеков). Core-тесты на CI не затрагиваются.
- **Накладка `once` + `protected` в оверлее** → Предупреждение об одноразовости
  остаётся видимым, цель скрыта — оба требования соблюдены.
- **Риск спутать маску с реальным значением** → Маска нередактируема/невыделяема, при
  раскрытии заменяется реальной целью с тем же `mono`-оформлением.
