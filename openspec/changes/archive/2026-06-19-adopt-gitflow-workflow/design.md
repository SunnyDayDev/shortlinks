## Context

Репозиторий shortlinks разрабатывается автором с помощью ассистента. Ранее процесс
не был зафиксирован, и часть изменений попадала прямо в `main`. Уже есть устоявшаяся
практика этой сессии: ветка → push → PR → merge-commit. Нужно закрепить её как
требование, а не держать только в памяти ассистента.

## Goals / Non-Goals

**Goals:**
- Зафиксировать gitflow-облегчённый процесс: `main` стабилен, работа — в ветках, мерж — через PR.
- Дать однозначные правила именования веток и условий мержа.
- Сделать процесс воспроизводимым и для автора, и для ассистента.

**Non-Goals:**
- Полный «классический» gitflow с `develop`/`release`/`hotfix`-ветками — избыточно для одиночного проекта.
- CI-пайплайн как таковой (его настройка — отдельная возможная работа); здесь лишь требование, что проверки должны быть зелёными.
- Изменение кода приложения.

## Decisions

- **Trunk-ветка — `main`, без `develop`.** Для соло-проекта вторая долгоживущая ветка не нужна; единственная стабильная ветка `main` + короткоживущие feature-ветки. Альтернатива (полный gitflow с `develop`) отклонена как оверхед.
- **Мерж merge-commit'ом (`--merge`), а не squash/rebase.** Сохраняет связь PR↔коммиты и историю веток; согласуется с уже выполненным мержем PR #1. Squash рассмотрен, но теряет промежуточные коммиты; rebase-merge усложняет восстановление контекста PR.
- **Префиксы веток `feat|fix|chore|docs`.** Простая, общеизвестная конвенция; согласуется с уже использованными именами (`chore/signing-and-spec-sync`).
- **Удаление ветки после мержа + ff-обновление локального `main`.** Держит список веток чистым и локальную копию в синхроне.
- **Branch protection для `main`** настраивается в GitHub (запрет push в `main`, требование PR). Делается вручную в настройках репозитория — это не редактируемый из репо артефакт, поэтому в задачах помечен как опциональный/ручной шаг.

## Risks / Trade-offs

- [Соло-разработчик может счесть PR-флоу избыточным для мелких правок] → польза в чистой истории и единообразии перевешивает; мелкие правки всё равно проходят быстрый self-merge.
- [Branch protection требует ручной настройки в GitHub и здесь не автоматизируется] → задокументировано как ручной шаг; даже без него правило соблюдается процессом.
- [Без CI «зелёные проверки» = ручной прогон сборки/валидации] → допустимо; требование сформулировано как «как минимум сборка и openspec validate».

## Migration Plan

1. Зафиксировать спеку `dev-workflow` в основных спеках (через sync/archive).
2. Отразить правило в `CLAUDE.md` (раздел рабочего процесса) и при желании в `README`.
3. (Опционально, вручную) включить branch protection для `main` в GitHub.

Откат: удалить спеку `dev-workflow` и упоминание в `CLAUDE.md`; технических последствий нет.
