# Design — .pen Merge Safety

## Context

`design/shortlinks.pen` — источник правды дизайна (change `adopt-pencil-design-system`). Тот
change по инерции из инструкций Pencil MCP утверждал, что файл «зашифрован» и недоступен
`Read`/`grep`/диффу. Проверка файла опровергает это.

Фактическая структура (проверено на текущем файле):

```
{ "version": "2.14",
  "themes": { "mode": ["light","dark"] },
  "variables": { <60 именованных токенов, часть с theme-вариациями> },
  "children": [ <8 top-level фреймов> ],
  "fileToken": "<uuid>" }
```

- 8 top-level `children`: 7 экранов + страница «Design System».
- 17 reusable-компонентов (мастеров) — **все внутри** ребёнка «Design System».
- 154 инстанса (`type:"ref"`) в экранах, ссылающихся на мастера; **0 висячих**.
- 794 узла с `id` — **все уникальны**; 46 различных ссылок `$var` — **все разрешаются**.

Дерево узлов связано ссылками: `ref.ref` → id мастера; ключи `descendants` → id/пути потомков;
значения свойств `"$name"` → `variables[name]`; `variables` с theme-вариациями → оси `themes`.
Это и определяет, когда текстовый JSON-merge даёт валидный результат.

## Goals / Non-Goals

**Goals:**
- Зафиксировать, что `.pen` — plain JSON: читается, диффается, мержится.
- Дать чёткую, проверяемую **модель безопасного слияния** (условия + фолбэк).
- Исправить неверную формулировку «зашифрован» в уже принятых спеке/`CLAUDE.md`.

**Non-Goals:**
- Автоматический git merge-driver для `.pen` (можно позже; здесь — модель и, опционально,
  валидатор-проверка).
- Изменение формата файла или реструктуризация дизайн-системы (напр. разнос мастеров по
  нескольким top-level детям ради параллельного мержа) — вне скоупа.
- Отмена правила «редактировать через Pencil MCP»: оно остаётся (сохранение инвариантов),
  меняется лишь его обоснование.

## Decisions

1. **Файл — plain JSON; Pencil MCP нужен для редактирования, не для чтения.**
   Read/grep/diff применимы. Авторские правки всё равно ведём через Pencil MCP, чтобы не
   нарушить инварианты (генерация уникальных `id`, целостность `ref`/`descendants`, соответствие
   схеме `version`). Ручная правка JSON допустима как исключение при разрешении merge-конфликта.

2. **Модель безопасного слияния — конъюнкция инвариантов.**
   Слияние = объединение веток безопасно, только если выполнены ВСЕ условия S1–S5:
   - **S1 (непересечение по детям).** Правки в разных top-level `children`. Добавление нового
     top-level ребёнка — тоже непересечение. Порядок top-level детей косметичен (позиция на
     холсте задаётся `x`/`y`), реордер массива безопасен.
   - **S2 (разрешимость переменных).** Каждый `"$name"` после слияния есть в `variables`.
   - **S3 (уникальность id).** Ни один `id` не дублируется после слияния.
   - **S4 (ссылочная целостность).** Каждый `ref` → существующий reusable-`id`; каждый ключ
     `descendants` → реальный путь потомка.
   - **S5 (аддитивность токенов/тем, единая схема).** `variables`/`themes` не задают один ключ
     разными значениями; `version` совпадает.

3. **Дизайн-система — единый merge-hotspot.**
   Т.к. все мастера и токены — в одном ребёнке «Design System», две ветки, обе меняющие
   дизайн-систему, всегда нарушают S1 → ручной мерж. Это осознанный трейд-офф текущей структуры;
   правка мастера при этом корректно распространяется на инстансы в экранах (инстанс наследует
   новый мастер и сохраняет свои оверрайды), так что «мастер в одной ветке + экран-потребитель в
   другой» — это S1-непересечение и безопасно.

4. **Фолбэк при нарушении любого из S1–S5.**
   Разрешить конфликт вручную в JSON (файл читаем) либо принять один из вариантов файла целиком
   (`git checkout --ours/--theirs`). Выбор одного варианта всегда даёт валидный файл.

5. **Проверяемость (опционально).**
   Инварианты S2–S4 механически проверяемы скриптом (парс JSON → уникальность `id`, разрешимость
   `$var` и `ref`). Такой валидатор может служить пост-merge-проверкой «безопасно ли смержено».
   Включаем как опциональную задачу, ядро изменения — документация.

## Risks / Trade-offs

- [Текстовый merge «чист», но результат семантически неожиданный] → S1 ограничивает автомерж
  непересекающимися детьми; для дизайн-системы (единый ребёнок) — только ручной мерж.
- [Коллизия сгенерированных `id` при слиянии больших добавлений] → маловероятна (случайные id),
  но S3 требует явной проверки; при дубле — ручное переименование одной стороны.
- [Кто-то воспримет «можно мержить» как «правь JSON руками»] → в документации подчёркнуто:
  авторство — через Pencil MCP; ручная правка только для разрешения конфликтов.
- [`fileToken`/`version` расходятся между ветками] → `fileToken` косметичен (взять любой);
  расхождение `version` = разные схемы → ручной разбор (S5).

## Migration Plan

1. Обновить спеку `design-file`: скорректировать требование про доступ (plain JSON, Pencil MCP —
   для инвариантов) и добавить требование модели безопасного слияния.
2. Поправить `dev-workflow`: убрать «файл зашифрован» из ремарки.
3. Обновить `CLAUDE.md` (конвенция дизайна): убрать «зашифрован», кратко изложить модель мержа.
4. (Опц.) добавить валидатор-скрипт инвариантов.
5. `openspec validate` → `/opsx:sync` → `/opsx:archive` (до PR, по gitflow), затем один PR.

Откат: вернуть прежние формулировки; кода нет — откат тривиален.
