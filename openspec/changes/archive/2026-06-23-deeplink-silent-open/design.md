## Context

`sl://link/<slug>` регистрируется через `CFBundleURLTypes`, открытие резолвит macOS
LaunchServices → запускает приложение-обработчик и доставляет URL в
`AppDelegate.application(_:open:)`. Сейчас `LSUIElement: false` (см. `project.yml`):
приложение — обычное, всегда с иконкой в Dock. Код уже пытается прятать окно
(`NSApp.hide(nil)` после фонового перехода), но Dock-иконка и кратковременный
перехват фокуса остаются.

Комментарий в `project.yml` фиксирует, что `false` выбирали ради «надёжной работы
окна и `sl://`». Это изменение пересматривает выбор: делаем агента (`.accessory`) с
**динамическим** повышением политики только когда реально нужно показать окно.

**Платформенное ограничение (неустранимое):** обработать кастомную схему «совсем без
запуска приложения» нельзя. LaunchServices сопоставляет схему `sl` с бандлом и обязана
запустить процесс-обработчик, чтобы доставить URL. «Не запускать приложение» как
буквальное требование невыполнимо; достижимо лишь убрать видимые признаки запуска —
иконку в Dock и перехват фокуса.

## Goals / Non-Goals

**Goals:**
- Фоновый переход (активная многоразовая ссылка без пароля, без режима подтверждения)
  происходит без иконки в Dock и без вывода окна.
- У приложения нет постоянной иконки в Dock — оно живёт в меню-баре.
- Когда нужен UI (пароль, ненайденная/заблокированная ссылка, режим подтверждения),
  окно показывается надёжно и поверх, затем приложение уходит в фон.
- Причина, по которой обработчик обязан запускаться, задокументирована.

**Non-Goals:**
- Полный отказ от запуска процесса при открытии `sl://` (невозможно на macOS).
- XPC/login-item/отдельный helper-демон для обработки схемы — избыточно для текущих
  задач; обработчиком остаётся само приложение.
- Изменение потоков пароля/подтверждения/потребления одноразовых ссылок по существу.

## Decisions

### 1. `LSUIElement: true` + динамическая `NSApp.setActivationPolicy`
Приложение становится агентом (`.accessory`): нет постоянной иконки в Dock, есть
меню-бар. Перед показом окна оверлея переключаемся в `.regular` и
`NSApp.activate(ignoringOtherApps:)`; после закрытия оверлея — обратно в `.accessory`.

- **Почему так:** даёт «тихий» фон по умолчанию и полноценное окно по требованию.
  Это штатный паттерн для menu-bar/agent-приложений на macOS.
- **Альтернативы:**
  - *Оставить `LSUIElement: false` и просто `NSApp.hide`.* Не убирает иконку в Dock и
    мерцание фокуса при каждом переходе — не решает задачу.
  - *Чистый агент без повышения политики.* SwiftUI `Window` у `.accessory`-приложения
    показывается ненадёжно/без фокуса ввода (известная проблема для парольного поля) —
    ровно тот риск, из-за которого исходно выбрали `false`. Динамическое повышение его
    закрывает.

### 1a. Окно — через AppKit (`NSWindow` + `NSHostingController`), а не сцена `Window`
Главное окно создаётся лениво в `AppDelegate` и показывается только по требованию;
SwiftUI-сцена `Window` убрана.

- **Почему так (выявлено при тестировании):** сцена `Window` выводит окно при запуске
  процесса. Поскольку обработчик `sl://` каждый раз запускает процесс, при тихом
  фоновом переходе окно успевало мигнуть на доли секунды, а `NSApp.hide` прятал его уже
  постфактум. Лениво создаваемое AppKit-окно при фоновом переходе **не создаётся вовсе**
  — мигать нечему. Заодно снимается гонка «`openMainWindow` ещё не привязан на cold
  launch»: замыкания показа/скрытия ставятся в `applicationDidFinishLaunching`.
- **Альтернатива:** `.defaultLaunchBehavior(.suppressed)` для сцены — только macOS 15+,
  а минимальная цель `14.0`.

### 2. Решение «нужен ли UI» остаётся в `AppModel`, переключение политики — в App-слое
`AppModel.handleIncoming`/`route` уже возвращают флаг «нужен UI» (`Bool`).
`AppDelegate.application(_:open:)` по этому флагу либо повышает политику и показывает
окно, либо выполняет фоновый переход и остаётся в `.accessory`. Возврат в `.accessory`
привязывается к закрытию оверлея (когда `redirectPhase`/`redirectSlug` очищается).

- **Почему так:** доменное решение не дублируется; App-слой отвечает только за
  активацию/окно. Согласуется с конвенцией «логику — в ядро, не в app».

### 3. Возврат в `.accessory` по завершению оверлея
После `consume`/отмены оверлей закрывается; в этот момент приложение демотируется в
`.accessory`. Реализуется через наблюдение за обнулением состояния редиректа или
закрытием окна `main`.

- **Риск гонки:** если демоут случится до первого показа окна — окно не покажется.
  Поэтому демоут — только по факту закрытия оверлея, а не сразу после показа.

## Risks / Trade-offs

- **[Окно у `.accessory` не получает фокус ввода для пароля]** → перед показом всегда
  `setActivationPolicy(.regular)` + `NSApp.activate(ignoringOtherApps: true)`; вернуться
  в `.accessory` только после закрытия оверлея.
- **[Мерцание Dock при повышении до `.regular`]** → допустимо: происходит только когда
  пользователю и так показывается окно (пароль/ошибка/подтверждение), а не в тихом
  фоне.
- **[Пользователь теряет привычную иконку в Dock]** → запуск окна доступен из меню-бара
  («Открыть окно», «Новая ссылка»); это сознательный переход к agent-модели.
- **[Регрессия открытия главного окна вручную]** → проверить, что пункты меню-бара и
  онбординг/настройки открывают окно (повышают политику) корректно.

## Migration Plan

1. `project.yml`: `LSUIElement: true`; `xcodegen generate` (регенерирует
   `Info.plist`/проект — оба не коммитятся как генерируемые? `Info.plist` под VCS,
   проверить и обновить вручную при необходимости).
2. Внедрить переключение `setActivationPolicy` в `AppDelegate` и точку возврата в
   `.accessory`.
3. Ручная проверка сценариев (фон / пароль / not-found / меню-бар).
4. Обновить `CLAUDE.md` (раздел про модуль App и ключевые решения) — зафиксировать
   agent-режим и платформенное ограничение.
5. Откат: вернуть `LSUIElement: false` и убрать переключение политики.
