## Context

UI приложения живёт в `Sources/ShortlinksApp/` (SwiftUI, `MenuBarExtra` + одно окно
через AppKit). Уже есть частичный задел: `Theme.swift` (enum `Theme` с палитрой и
хелперами `Color(hex:)`/`Color.dyn`) и `Components.swift` (`StatusPill`, `TargetIcon`,
`TagChip`, `FlowLayout`). Но слой неполный и его массово обходят: см. метрики в
`proposal.md` (77 `.font(.system(size:))` с 15 кеглями, 17 inline `Color(hex:)` во вью,
8 радиусов, дрейф серых, ~5 inline-копий primary-кнопки и 4 — карточки).

Ограничения проекта (CLAUDE.md, design.md bootstrap): Swift language mode 5 (без strict
concurrency), самоподписанная ручная подпись, GUI на CI не собирается (проверяется только
ядро), проект генерируется `xcodegen` из `project.yml` (список файлов явный). CLI не имеет
UI и не зависит от слоя представления.

Пользователь выбрал: **единый статический слой токенов**, тема следует системной
light/dark (без рантайм-переключения и без UI выбора темы); **миграция всех экранов** в
рамках этого изменения.

## Goals / Non-Goals

**Goals:**
- Единый источник правды для цвета/типографики/отступов/радиусов — смена палитры или
  брендинга правкой одного слоя.
- Унификация и устранение дублирования: повторяющиеся паттерны (кнопки, карточка,
  заголовок секции, поле, code-box, icon-плитка) — как переиспользуемые компоненты/стили.
- Упростить создание нового UI: семантические токены и готовые компоненты вместо
  «магических» чисел.
- Полная миграция всех экранов с визуальным паритетом.

**Non-Goals:**
- Рантайм-переключение тем и пользовательский выбор темы (Environment-инъекция,
  протокол темы) — сознательно вне объёма; архитектура централизует токены так, чтобы
  такой переход позже был механическим.
- Редизайн/изменение внешнего вида — это рефактор с паритетом, а не новый визуал.
- Изменения в `ShortlinksCore`, CLI, формате данных, схеме `sl://`.
- Вынос дизайн-системы в отдельный фреймворк-таргет/пакет.

## Decisions

### 1. Статический namespace токенов (не Environment-инъекция)
Токены — это `enum`-namespace со статическими членами (как текущий `Theme`), а не
`@Environment`-инъектируемый протокол темы. Соответствует выбору пользователя и цели
«в одном месте»: один слой задаёт все значения, API простой (`Color.Token.accent`,
`Font.Token.body`), нет прокидывания темы через окружение.
- *Альтернатива* — протокол `Theme` + `@Environment(\.theme)`: нужен для рантайм-смены
  палитры/нескольких брендов, но это лишняя инфраструктура под несуществующее
  требование. Отвергнуто; централизация токенов оставляет путь к ней открытым.

### 2. Двухуровневая структура цвета: foundation → semantic
- **Foundation** — сырая палитра (приватные hex-константы, производные от макета
  `_design/`): единственное место с `Color(hex:)`.
- **Semantic** — роли поверх foundation: `accent`, `accentHover`, `surface` (карточка),
  `surfaceSubtle`, `content` (фон контента), `sidebar`, `separator`, `textPrimary`,
  `textSecondary`, `code`, `iconTileBg`/`iconTileFg`, `onceAccent`/`onceText`,
  `activeAccent`, `destructive`/`destructiveBg`, плюс `status(_:)` для статусов ссылок.
  Адаптивность к теме — через существующий `Color.dyn(light, dark)` и системные
  `NSColor` (`separatorColor`, `controlBackgroundColor`, `textBackgroundColor`), которые
  уже корректно следуют теме. Вью ссылаются только на semantic-уровень.
- Зеркалит подход референса RuStore (foundation → semantic → компоненты), но облегчённо
  и без отдельных контраст-тем.

### 3. Типографика как именованная шкала
Токены-шрифты возвращают `Font`: например `title`/`title2`/`headline`/`body`/
`bodyMedium`/`callout`/`caption`/`caption2` и моно-варианты (`mono`, `monoSmall`).
Чтобы держать **визуальный паритет**, существующие кегли отображаются в шкалу
консервативно: каждый текущий размер — в ближайший именованный токен; где унификация
сместила бы пиксели заметно, токен сохраняет точное значение. Цель — убрать
произвольные `.system(size:)` из вью, не «причёсывая» макет.

### 4. Шкалы отступов и радиусов
- **Spacing** — числовая шкала из реально используемых шагов (напр. 2/4/6/8/12/16/22).
- **Radius** — `sm`/`md`/`lg` (примерно 7/10/12) + точечные значения для пилюль/плиток.
  Текущие 8 радиусов сводятся к шкале; где разный радиус был случайным (primary-кнопка
  7/8/9) — выбирается один. Основные внешние отступы экранов выражаются через spacing-
  токены; мелкая внутренняя вёрстка может остаться числами, если это не цвет/кегль/радиус.

### 5. Компоненты и стили
Извлекаются как `ButtonStyle` / `ViewModifier` / небольшие `View`:
- `PrimaryButtonStyle` (акцент, белый текст, радиус, опц. иконка) — заменяет ~5 inline-
  копий; `SecondaryButtonStyle`, `DestructiveButtonStyle`.
- `.card()` модификатор (surface + рамка + радиус) — заменяет `card`/`infoCard`/grid-
  ячейку/`LinkRow`-фон.
- `SectionLabel` — объединяет `groupLabel`(Settings) и `sectionLabel`(Sidebar).
- `FieldBox`/`InputStyle` — `boxBg` из CreateSheet.
- `CodeBox` — моно-блок (RedirectOverlay, Settings cliPathHint, LinkDetail target).
- `IconTile` — плитка с SF Symbol на цветном фоне (Sidebar row, Settings privacy,
  HowItWorks steps).
`StatusPill`/`TargetIcon`/`TagChip` остаются, но переводятся на токены (включая hardcoded
`0x3F6BB5`/`0x2A6FDB` в `TagChip`).

### 6. Размещение: каталог внутри `ShortlinksApp`, без нового таргета
DS живёт в `Sources/ShortlinksApp/DesignSystem/` (подгруппы `Tokens/`, `Styles/`,
`Components/`). Отдельный фреймворк-таргет не вводится: единственный потребитель — app
(CLI без UI), а новый таргет потянул бы за собой настройку подписи и усложнение
`project.yml`. Если позже появится второй UI-потребитель — вынос будет отдельным
изменением.

### 7. Контроль инварианта (запрет сырых значений)
Чтобы «единый источник» не разъехался, добавляется простая grep-проверка: во `Views/` и
`MainView.swift` не должно быть `Color(hex:`, прямых `*.BackgroundColor` и
`.font(.system(size:`. Оформляется как скрипт/документированная проверка; включение в
CI — опционально (GUI на CI не собирается, но grep дешёв и не требует сборки).

### 8. Шкала spacing под ритм макета (пиксель-сохраняющая)
Макет построен на ритме ~11/14/18/22/26, а не на 4/8-сетке. Чтобы убрать «магические»
отступы, **не ломая визуальный паритет** (у пользователя ожидается визуальная сверка),
`Spacing` определяется под фактический ритм (2/4/6/8/12/14/18/22/26/32): доминирующие
значения (22/18/14/26) остаются точными, мелкий хвост (3/5/7/9/13) снапится к ближайшему
шагу в пределах ≤2px. Так каждое значение становится именованным токеном без сдвига
заметной вёрстки.
- *Альтернатива* — строгая 4/8-сетка: «чище» как шкала, но сдвигает 3 самых частых
  отступа на 2px по всем экранам = видимый передел. Отвергнуто сейчас; возможно отдельным
  визуальным изменением.

### 9. Размеры через `Size` и впитывание в компоненты
Фиксированные размеры (ширины окна/листа/оверлея, высоты контролов/полей, ширины
колонок-меток, max-ширины контента) выносятся в именованные токены `Size` и, где это
повтор, **впитываются в компоненты** (поле само знает высоту, контейнер экрана —
max-ширину). Во вью не остаётся голых чисел в `frame`/`padding`/`spacing`.

### 10. Структура atoms/molecules
Дизайн-система разносится на `Tokens/` (цвет/типографика/spacing/size), `Atoms/`
(примитивы и стили: кнопки, поверхности, `SectionLabel`, `StatusPill`, `TagChip`,
`TargetIcon`, `IconTile`, `FlowLayout`) и `Molecules/` (составные: `ScreenContainer`,
`LabeledField`, `InfoRow`, `SidebarItem`, `SettingsRow`/`SettingsCard`). Это первый
проход атомарной структуры — не полная методология; организмы/экраны пока остаются вью.

### 11. Расширение линта на spacing/size
`Scripts/ds-lint.sh` дополнительно запрещает во `Views/` голые числа в
`.padding(`/`spacing:`/`frame(width|height|maxWidth:` — допустимы только `Spacing`/`Size`
(или внутренняя вёрстка компонентов в слое DesignSystem).

## Risks / Trade-offs

- **Визуальный дрейф при миграции** → Мигрировать поэкранно; для каждого значения
  заводить токен с тем же (или сознательно унифицированным) значением; сверять каждый
  экран с домиграционным видом и макетом `_design/` перед коммитом.
- **Слишком агрессивная рационализация шкалы меняет пиксели** → Приоритет паритета:
  сохранять точные кегли/радиусы как именованные токены там, где округление заметно;
  унифицировать только явные дубликаты и дрейф (два серых → один).
- **Статический API закрывает рантайм-темизацию** → Принято осознанно (вне объёма);
  централизация токенов делает будущий переход на Environment механическим.
- **GUI не собирается на CI** → DS проверяется локальной сборкой app + grep-линтом;
  `ShortlinksCoreTests` остаются гарантией для ядра.
- **Регенерация проекта** → После добавления файлов в `DesignSystem/` обязательно
  обновить `project.yml` и прогнать `xcodegen generate` (явный список файлов).

## Migration Plan

1. Слой токенов (`Tokens/`: Color, Typography, Spacing, Radius) + `project.yml` +
   `xcodegen generate`; сборка app зелёная.
2. Компоненты/стили (`Styles/`, `Components/`) поверх токенов; перевод существующих
   `StatusPill`/`TargetIcon`/`TagChip`.
3. Поэкранная миграция (по одному файлу, с визуальной сверкой): SidebarView, MainView,
   LinkListView, LinkDetailView, CreateSheet, SettingsView, RedirectOverlay,
   HowItWorksView.
4. Удаление устаревших inline-хелперов (`boxBg`, локальные `card`/`groupLabel` и т.п.).
5. Grep-линт проходит (нет сырых цветов/кеглей/радиусов во вью); финальная сборка app +
   `ShortlinksCoreTests`.

Откат: изменения изолированы в слое представления app; при проблеме экран можно вернуть
к прежней inline-вёрстке, ядро и данные не затронуты.
