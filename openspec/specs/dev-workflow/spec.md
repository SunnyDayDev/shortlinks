# dev-workflow Specification

## Purpose

Процесс разработки shortlinks на основе gitflow: правила ветвления, запрет прямых
коммитов в `main`, требования к Pull Request и слиянию.

## Requirements

### Requirement: Ветка под каждое изменение
Любой новый функционал, исправление или правка SHALL разрабатываться в отдельной
ветке, ответвлённой от актуального `main`. Прямые коммиты в `main` SHALL быть
запрещены.

#### Scenario: Начало работы над изменением
- **WHEN** начинается работа над новым функционалом или правкой
- **THEN** создаётся отдельная ветка от свежего `main`, и коммиты идут в неё, а не в `main`

#### Scenario: Попытка коммита прямо в main
- **WHEN** есть незакоммиченные изменения и текущая ветка — `main`
- **THEN** перед коммитом создаётся ветка, и `main` остаётся без прямых коммитов

### Requirement: Конвенция именования веток
Имя ветки SHALL начинаться с типа изменения и краткого описания в kebab-case:
`feat/…` (функционал), `fix/…` (исправление), `chore/…` (обслуживание),
`docs/…` (документация/спеки).

#### Scenario: Имя ветки под новый функционал
- **WHEN** создаётся ветка под новый функционал «экспорт ссылок»
- **THEN** ветка называется по шаблону, напр. `feat/links-export`

### Requirement: Интеграция через Pull Request
Изменения SHALL вливаться в `main` только через Pull Request. PR SHALL иметь
осмысленные заголовок и описание (что и зачем) и SHALL быть смержен только после
успешных проверок. Сборка и юнит-тесты `ShortlinksCoreTests` SHALL выполняться
автоматически через CI (GitHub Actions) при каждом PR; дополнительно, если затронуты
спеки, выполняется `openspec validate`.

#### Scenario: Открытие PR
- **WHEN** работа в ветке завершена и запушена
- **THEN** открывается PR в `main` с заголовком и описанием изменений, и CI
  автоматически запускает сборку и тесты

#### Scenario: Блокировка мержа при падении проверок
- **WHEN** проверки PR (CI-сборка/тесты или валидация спеков) не прошли
- **THEN** PR не мержится до их устранения

### Requirement: Слияние и уборка ветки
После аппрува и зелёных проверок PR SHALL вливаться в `main` merge-commit'ом, а
ветка-источник SHALL удаляться (на remote и локально). Локальный `main` после мержа
SHALL синхронизироваться с `origin/main`.

#### Scenario: Мерж и удаление ветки
- **WHEN** PR одобрен и проверки зелёные
- **THEN** PR мержится в `main` merge-commit'ом, ветка удаляется, локальный `main` подтягивает изменения

### Requirement: Синхронизация дизайн-файла при изменениях UI
Pull Request с изменением UI приложения SHALL синхронизировать дизайн-файл: PR,
меняющий внешний вид экранов, компонентов или токенов в `Sources/ShortlinksApp/`,
включает соответствующее обновление `design/shortlinks.pen` — либо явное указание в
описании PR, что визуальных изменений нет (например, рефактор без изменения внешнего
вида). Обновление дизайн-файла SHALL соответствовать дизайн-системе (использовать её
переменные и мастера-компоненты). Правило соблюдается по договорённости и проверяется
на ревью (техническое принуждение невозможно: branch protection недоступна). Файл — это
plain JSON, поэтому дифф дизайн-файла читаем на ревью, а параллельные правки допустимо
сливать по модели безопасного слияния (см. capability `design-file`).

#### Scenario: PR с новым экраном
- **WHEN** открывается PR, добавляющий или визуально меняющий экран приложения
- **THEN** в PR входит обновлённый `design/shortlinks.pen` с соответствующим фреймом,
  собранным из компонентов дизайн-системы

#### Scenario: PR с рефактором без визуальных изменений
- **WHEN** открывается PR, затрагивающий код вью, но не меняющий внешний вид
- **THEN** дизайн-файл не обновляется, а в описании PR явно указано, что визуальных
  изменений нет

#### Scenario: Ревью замечает рассинхрон
- **WHEN** на ревью PR внешний вид изменён, но дизайн-файл не обновлён и оговорки в
  описании нет
- **THEN** PR не мержится до обновления дизайн-файла или явной оговорки
