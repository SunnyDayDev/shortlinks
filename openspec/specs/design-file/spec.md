# design-file Specification

## Purpose

`.pen`-файл `design/shortlinks.pen` (редактор Pen, прежнее название — Pencil) как
источник правды дизайна UI: его структура, правила версионирования и редактирования,
а также соответствие токенов и компонентов дизайн-файла слою `DesignSystem` в коде.

## Requirements

### Requirement: Дизайн-файл как источник правды дизайна
`.pen`-файл `design/shortlinks.pen` SHALL являться источником правды дизайна UI
приложения. Файл SHALL версионироваться в git вместе с кодом. Файл представляет собой
**обычный валидный JSON** (`version`, `themes`, `variables`, `children`, `fileToken`) —
он читается и сравнивается (diff) стандартными инструментами. **Авторские правки** SHALL
выполняться инструментами Pen (MCP), чтобы сохранять структурные инварианты
(глобально уникальные `id`, целостность `ref`/`descendants`, соответствие схеме
`version`); ручная правка JSON допустима как исключение — при разрешении merge-конфликтов.
Прежний HTML-макет `_design/` SHALL быть удалён из репозитория (доступен в истории git).

#### Scenario: Файл версионируется вместе с кодом
- **WHEN** дизайн изменён в `design/shortlinks.pen`
- **THEN** изменение фиксируется коммитом в той же ветке/PR, что и связанные правки
  кода, и попадает в историю git

#### Scenario: Авторская правка — через Pen, чтение/дифф — свободно
- **WHEN** требуется изменить дизайн
- **THEN** правка ведётся через Pen (MCP), чтобы не нарушить инварианты; при этом
  файл остаётся plain JSON и его допустимо читать и сравнивать (diff) обычными
  инструментами, а править JSON вручную — только при разрешении merge-конфликта

### Requirement: Структура дизайн-файла
Дизайн-файл SHALL содержать страницу «Design System» (палитра цветовых переменных с
темами light/dark, типографическая шкала, шкалы отступов и радиусов, галерея
мастеров reusable-компонентов) и экраны приложения как отдельные top-level фреймы.
Повторяющиеся паттерны UI в экранах SHALL быть инстансами мастеров-компонентов, а не
дублирующей «сырой» вёрсткой; прямая вёрстка допустима только для одноразовых
композиций.

#### Scenario: Новый экран собирается из компонентов
- **WHEN** в дизайн-файл добавляется новый экран с кнопками, полями, строками списка
  или другими существующими паттернами
- **THEN** эти паттерны вставляются как инстансы мастеров со страницы «Design System»,
  и правка мастера распространяется на новый экран

#### Scenario: Правка компонента распространяется на все экраны
- **WHEN** меняется мастер-компонент (например, стиль кнопки `Button/Primary`)
- **THEN** все экраны, использующие его инстансы, обновляются без поэкранных правок

### Requirement: Парность токенов и компонентов с кодом
Токены и компоненты дизайн-файла SHALL соответствовать слою `DesignSystem` кода с
согласованным неймингом (например `accent` ↔ `Theme.accent`, `Button/Primary` ↔
`PrimaryButtonStyle`, `space-16` ↔ `Spacing.s16`). Новый токен или компонент SHALL
добавляться парно: переменная/мастер на странице «Design System» дизайн-файла и
токен/вью в коде. Расхождения нейминга или значений SHALL устраняться при первом
обнаружении.

#### Scenario: Новый цветовой токен
- **WHEN** в UI требуется новый семантический цвет
- **THEN** он добавляется и как переменная дизайн-файла (со значениями light/dark),
  и как токен `Theme` в коде, под согласованным именем

#### Scenario: Новый переиспользуемый компонент
- **WHEN** в UI появляется новый повторяющийся паттерн
- **THEN** создаются мастер-компонент в галерее дизайн-файла и соответствующий
  atom/molecule в коде

### Requirement: Модель безопасного слияния дизайн-файла
Слияние (merge) параллельных правок `design/shortlinks.pen` (plain JSON) SHALL
считаться безопасным — объединение обеих веток без ручного разбора — только при
одновременном выполнении всех условий:
1. правки затрагивают **разные top-level элементы `children`** (разные фреймы
   экранов/областей); добавление нового top-level элемента — тоже непересечение;
2. все ссылки `$variableName` присутствуют в `variables` после слияния;
3. все `id` узлов остаются **глобально уникальными** после слияния;
4. **ссылочная целостность**: каждый `ref` разрешается в существующий
   reusable-компонент, каждый ключ `descendants` — в реальный путь потомка;
5. правки `variables`/`themes` аддитивны и не задают один ключ разными значениями;
   `version` совпадает.
Все мастера-компоненты и токены живут в одном top-level элементе «Design System»,
поэтому две ветки, обе меняющие дизайн-систему, нарушают условие 1 и требуют ручного
слияния. При невыполнении любого из условий слияние SHALL разрешаться вручную в JSON
либо выбором одного из вариантов файла целиком.

#### Scenario: Непересекающиеся экраны сливаются автоматически
- **WHEN** одна ветка меняет только экран A, другая — только экран B (разные top-level
  `children`), и после слияния все `$var`/`ref`/`id`-инварианты сохранены
- **THEN** ветки объединяются без ручного разбора — валидный файл со всеми правками

#### Scenario: Правки одного элемента разрешаются вручную
- **WHEN** обе ветки меняют один и тот же top-level элемент (например обе — страницу
  «Design System»), или возникает конфликт переменной/темы/`id`, или висячий `ref`
- **THEN** конфликт разрешается вручную в JSON либо выбором одного из вариантов файла
  целиком (результат остаётся валидным `.pen`)

#### Scenario: Проверка инвариантов после слияния
- **WHEN** после слияния нужно убедиться, что файл валиден
- **THEN** проверяется, что JSON парсится, все `id` уникальны, а все `$variableName` и
  `ref` разрешаются; при нарушении — слияние считается небезопасным и переделывается
